# プラグイン更新後も設定を維持する

Category: `enhancement`
Status: `ready-for-agent`

## 背景

OrcaSlicerはプラグイン設定を`orca_plugins/config.json`へ保存し、エントリをwheelのファイル名由来の`plugin_key`で識別する。`plugin_key`にはバージョンが含まれるため、プラグインを更新すると別エントリとして扱われ、利用者が変更した設定は引き継がれず既定値に戻る。

実機で確認した内容は次のとおり。

```json
{"config":[
  {"capability":"Hole Reinforcement Detector PoC","plugin_key":"hole_reinforcement_detector_poc","plugin_version":"0.01","cap_config":{...}},
  {"capability":"Hole Reinforcement","plugin_key":"orcaslicer_hole_reinforcement-0.0.1-py3-none-any","plugin_version":"0.0.1","cap_config":{...}}
]}
```

古いエントリは削除されず残り続ける。PoC版のエントリが正式版のエントリと並存していることがその実例である。

設定の永続化はホスト側が持っている。設定UIは`window.orca.saveConfig(config)`と`window.orca.getConfig()`を呼ぶだけで（`src/orcaslicer_hole_reinforcement/config_ui.py`）、プラグインは保存先も保存キーも制御できない。

issue16では、この挙動を`README.md`、`CHANGELOG.md`、`docs/release-checklist.md`へ「更新すると設定が既定値へ戻る」と明記して回避した。文書による周知であり、解決ではない。

## 期待する結果

バージョンを上げても、利用者が設定した値が更新後のプラグインへ引き継がれる。引き継ぎに失敗した場合は既定値で動作し、スライスを妨げない。

## 調査すべき選択肢

いずれも未検証であり、実装方針の決定前に妥当性を確認する。

- **旧エントリからの移行**: 起動時またはスライス時に`orca_plugins/config.json`を直接読み、`capability`（`Hole Reinforcement`）が一致する旧`plugin_key`のエントリから設定を引き継ぐ。`capability`はバージョンに依存しないため対応付けの鍵になりうる。ホストが所有するファイルを読むことの是非と、書き込みが必要かを確認する
- **バージョン非依存の保存先へ複製**: プラグイン側で設定のコピーをバージョンを含まないパスへ保存し、ホスト設定が既定値のときに復元する。展開先（`__whl_extracted__`配下）はバージョンに依存するため保存先にできない。`diagnostic.jsonl`と同じく`Path(__file__)`起点で解決している現在の方式（`slicing_capability.py:248`）をそのまま流用できない点に注意する
- **設定のエクスポート／インポート**: 設定UIへ手動の書き出し・読み込みを追加する。自動ではないが、ホストの挙動に依存しない
- **本体側の改善**: OrcaSlicerが`plugin_key`ではなくプラグイン名で設定を保持するよう提案する。`.install_state.json`はバージョンを含まない`plugin_name`（`orcaslicer-hole-reinforcement`）を保持しているため、キーの候補は存在する。ただし本体の変更を待つことになる
